PHASE 2 — ARCHITECTURE AND ENGINEERING DECISIONS
======================================================================

Propose an architecture that fits the actual requirements and
complexity. Prefer a modular, layered design where useful, but do not
force unnecessary abstractions or folders.

Consider these boundaries: - Routes: map URLs and middleware to
controllers. - Controllers: handle HTTP request/response concerns
only. - Services: implement application and business logic. -
Repositories/data-access layer: encapsulate persistence operations. -
Validation: validate external input at system boundaries. - Middleware:
authentication, authorization, request context, security, and error
handling. - Config: validated runtime configuration. - Database:
connection lifecycle and database-specific setup. -
Constants/enums/types/interfaces: shared domain and application
definitions. - Views: EJS presentation templates and partials. - Public
assets: browser-delivered static assets. - Tests: unit, integration, and
end-to-end tests as appropriate.

Architecture rules: 1. Avoid database queries in controllers and EJS
templates. 2. Avoid business logic in routes and presentation templates.
3. Avoid circular dependencies. 4. Keep module boundaries clear. 5.
Prefer dependency inversion where it improves testability and reduces
coupling. 6. Use dependency injection where it is useful; do not
introduce a container merely for fashion. 7. Keep shared code genuinely
shared. Do not create giant common folders containing unrelated code. 8.
Do not create a service/repository/interface for every trivial operation
automatically. Add layers when they provide meaningful separation,
reuse, or testability. 9. Define module ownership and allowed dependency
directions. 10. Document important architectural choices and their
trade-offs.

PHASE 3 — CODING AND TYPESCRIPT STANDARDS
======================================================================

Establish standards for the following.

A. TypeScript - Use strict TypeScript settings, subject to compatibility
with the existing codebase. - Avoid any. Prefer unknown for untrusted
values and narrow types safely. - Give exported functions and public
APIs explicit, meaningful types. - Use interfaces, type aliases,
generics, and discriminated unions appropriately. - Avoid unsafe type
assertions and non-null assertions. - Do not silence compiler errors
with broad suppressions. - Validate and narrow data received from HTTP
requests, environment variables, external APIs, queues, and database
boundaries. - Keep types close to their owning module unless genuinely
shared. - Avoid duplicate or conflicting type definitions.

B. Constants, enums, and domain values - Centralize reusable
business/domain values such as statuses, event names, roles, permission
identifiers, payment methods, and subscription states. - Use enums,
as const objects, or union types according to the use case; do not use
enums automatically for every value. - Avoid duplicated business-related
string literals and magic numbers. - Avoid hardcoded secrets,
environment-specific values, API endpoints, and configuration. - Put
configuration in validated configuration modules backed by environment
variables. - Do not create constants for every one-off local string or
obvious implementation detail. Avoid needless indirection. - Preserve
externally mandated values exactly when they form part of an API,
database, provider, or protocol contract.

C. Naming and organization - Define consistent naming conventions for
files, directories, classes, functions, variables, types, interfaces,
enums, constants, and environment variables. - Prefer descriptive names
over cryptic abbreviations. - Keep functions focused and reasonably
small. - Avoid deeply nested conditionals and excessive parameter
lists. - Prefer early returns where they improve clarity. - Comment on
intent, constraints, and non-obvious decisions, not obvious code. - Do
not add comments that merely restate the code.

D. General code quality - Apply SOLID, DRY, KISS, separation of
concerns, and single responsibility where appropriate. - Prefer
composition over inheritance when it improves clarity. - Avoid premature
optimization and overengineering. - Avoid duplicated logic, but do not
abstract unrelated code just because it looks similar. - Handle
asynchronous operations explicitly and avoid unhandled promise
rejections. - Clean up resources such as timers, streams, connections,
and listeners. - Do not use console.log as the production logging
strategy.

PHASE 4 — DATABASE ENGINEERING STANDARDS
======================================================================

Base this document on the actual database identified in
requirements/code. Do not assume MongoDB, MySQL, PostgreSQL, or another
database if it is not established.

Cover: - Connection lifecycle and pooling. - Typed data
models/documents. - Repository/data-access boundaries. - Input
validation and data integrity. - Index design and query performance. -
Projection and avoiding unnecessary data retrieval. - Pagination and
filtering. - Atomic updates and concurrency. - Transactions where
required for correctness. - Idempotency for retryable workflows and
event processing. - Timeouts and database error handling. - Migration
and schema evolution practices. - Backup, restore, and recovery
considerations. - Sensitive data handling and access control. - Query
observability without logging sensitive values.

Rules: 1. Never run destructive database operations without explicit
authorization. 2. Never assume records can be deleted or overwritten. 3.
Do not put database credentials in source code or documentation. 4. Do
not expose raw database errors to clients. 5. Do not claim an index,
transaction, or migration exists unless verified. 6. Document data
consistency and concurrency risks for critical workflows.

PHASE 6 — EJS FRONTEND STANDARDS
======================================================================

The backend also serves frontend pages through EJS. Define a clear
presentation architecture.

Cover: - EJS layouts and reusable partials. - View directory
organization. - Route/controller-to-view data contracts. - Form
submission and server-side validation. - Browser-side validation as a
usability aid only. - Static asset organization. - CSS and browser
JavaScript organization. - Responsive layout conventions. - Error,
empty, loading, and success states where applicable. - Session-aware
rendering where applicable. - Accessibility basics. - Cache behavior for
static assets where appropriate.

Security rules: - Use escaped EJS output (<%=) for untrusted/dynamic
values by default. - Use unescaped output (<%-) only for explicitly
trusted, safely generated HTML or trusted partial inclusion. Never use
it for unsanitized user input. - Do not expose environment variables,
secrets, internal tokens, or privileged backend data to templates or
browser code. - Prevent XSS and CSRF according to the application’s
rendering and session model. - Do not put business logic or database
operations in EJS templates. - Keep browser code separate from templates
where practical.
